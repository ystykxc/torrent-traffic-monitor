## 一、调研范围与选取标准

按你的要求，优先选取「使用范围广、经过大量人员验证」的项目，分四层取样，避免只拿小众玩具项目做对比：

| 层次 | 代表项目 | 选取理由 |
|---|---|---|
| 下载器自带 / 第三方 WebUI | qBittorrent WebUI、VueTorrent、Flood、Transmission Web UI / Web Control | 装机量最大的 BT 客户端生态，实时速率展示的「事实标准」 |
| 通用监控 / 时序栈 | Prometheus + Grafana + `qbittorrent-exporter`、Netdata、Glances、vnStat、ntopng | 工业级采集、存储、降采样、告警，用户基数极大 |
| 轻量自托管监控 | Beszel、Homepage / Homarr（仪表盘聚合） | 与本项目同为「单容器 / 轻量 / 自托管」定位，架构可比性最强 |
| PT 垂直生态 | PT Nexus（sqing33/PTNexus） | 与本项目同为「多下载器流量统计 + 图表」，口径与交互直接对标 |

## 二、同类项目逐一分析

### 2.1 qBittorrent WebUI（及 qbittorrent-nox）

qBittorrent 自带 AJAX Web UI，headless 版 `qbittorrent-nox` 默认监听 8080。核心接口是
`/api/v2/sync/maindata` 的**增量同步（rid）**：客户端带 `rid` 请求，服务端只返回本轮变化的
`server_state` 字段。本项目 `clients.py` 正是复刻了这套机制，并针对「空闲轮次
`alltime_dl/alltime_ul` 整个缺席」做了缓存补值（v15 口径）——这一点和上游行为一致，属于正确实现。

关键差异：**qB WebUI 只展示当前状态，不做长期流量记账**，历史总量依赖下载器自身的累计计数器。
本项目额外承担了「跨容器重启、跨采样间隔的持久化统计」，这是上游不解决的问题，也是本项目的主要价值。

> 官方与社区反复强调：Web UI 本质是「能往服务器写文件的控制面板」，**绝不应直接暴露公网**，
> 必须开认证。([qBittorrent 官方](https://www.qbittorrent.org/)、[对比评测](https://homelabcompass.com/compare/qbittorrent-vs-transmission))

### 2.2 VueTorrent / Flood

- **VueTorrent**：Vue 3 + TypeScript + Pinia 的 qB 替代前端，约 7k star，[架构分层清晰](https://blog.csdn.net/gitblog_00562/article/details/157085097)（Core 组件 / Services API 抽象 / 状态管理）。实时数据用**智能轮询 + 增量更新**，官方评测称同步延迟 < 500 ms。它把「展示层」与「下载器 API」彻底解耦。
- **Flood**：Node.js + React + TypeScript，[约 2.9k star、100+ 贡献者、v4.16.3](https://discovergit.app/repo/jesec/flood/review)，一套后端同时管 rTorrent / qBittorrent / Transmission，带 OpenAPI 文档。定位是「多客户端统一管理」，不是流量统计。

二者共同点：**只做实时展示与操作，不落库做长期统计**；前端工程化（组件化、类型安全、状态管理）远强于本项目的原生 JS。但代价是构建链、依赖体积、部署复杂度都高得多。

### 2.3 Prometheus + Grafana + qbittorrent-exporter

这是「下载器流量统计」最主流的工业方案。典型 exporter 如
[esanchezm/prometheus-qbittorrent-exporter](https://github.com/esanchezm/prometheus-qbittorrent-exporter)（Python，约 197 star，持续维护至 2026-10）、
[martabal/qbittorrent-exporter](https://github.com/martabal/qbittorrent-exporter)（Go，镜像约 10 MB）。

- **采集模型**：Prometheus **pull（拉取）**，exporter 被抓取时才向 qB 取一次数，暴露 `counter` 类型的
  `qbittorrent_alltime_dl_total` / `..._ul_total` 等累计计数器。
- **流量计算**：由 PromQL `rate()` / `increase()` 在查询时从 **counter 差值**推导，天然处理计数器回退、重启、抓取间隔变化。
- **存储**：Prometheus TSDB 自带**多级降采样与保留策略**；Grafana 负责任意时间范围的可视化。

> 这一套与本项目的口径**本质相同**：都认「累计计数器差值」，都不用「瞬时速率 × 时间」反推流量。
> 本项目 `collector.py::_increment()` 的 `ok / no_base / reset / spike / missing` 五态判定，等价于
> Prometheus 对 counter 的 reset 处理，属于**正确且经过验证的算法选择**。

差别在于：Prometheus 把「差值计算」推迟到查询时、存储层统一；本项目在采集时就把差值分摊进
`hourly` 表（`db.record_traffic_sample()`），**写时聚合、查时只读**。后者对 SQLite 更友好、查询更轻，
但牺牲了「 retroactive 重算」能力（见第五节）。

### 2.4 Netdata / Glances / vnStat / ntopng

| 项目 | 采集 | 存储 / 降采样 | 实时通道 | 适用面 |
|---|---|---|---|---|
| **Netdata** | 每台机器一个 agent，插件化采集（含 eBPF） | 自研 dbengine，**最多 5 级分辨率分层**（秒 / 分 / 时），约 0.5 字节/样本 | 内嵌 Web + REST API，近实时 | 800+ 集成，企业级 |
| **Glances** | 单机 Python + psutil | **无历史**（纯实时快照） | Web UI / REST（v4.5 起 token 认证） | [27k+ star，13 年历史](https://selfhosting.sh/compare/glances-vs-beszel) |
| **vnStat** | 读内核网卡计数，守护进程周期写 | 轻量数据库，**按小时 / 日 / 月**预聚合 | `vnstat -l` 实时 | 各 Linux 发行版标配 |
| **ntopng** | libpcap / PF_RING 抓包 + NetFlow/sFlow | Redis 缓存 + **RRD 环形数据库**（小时~年级回溯） | WebSocket 发布订阅 | 1998 年至今，网络工程师标配 |

这里最值得本项目借鉴的是 **Netdata / Beszel 的「多级分辨率分层」**：原始数据高分辨率短期保留，
自动聚合成分 / 时 / 天级长期保留。本项目已有雏形——`samples`（细粒度速率，保留 7 天）+ 
`hourly`（小时桶，永久）+ `traffic_samples`（v33 新增，流量统计采样）——但**分层是手工维护的两张表，
不是自动 rollup**，长窗口查询要 `UNION ALL` 拼接（见第五节）。

### 2.5 Beszel

[Beszel](https://beszel.dev/zh/guide/what-is-beszel) 是 2024 年发布的 Go 轻量监控，Hub（PocketBase + SQLite）
+ Agent（30–50 MB 内存）的 Hub-and-Spoke 架构，两年内成为 homelab 主流（数万 star）。几个设计和本项目高度呼应：

- **Hub 用 SQLite 而非时序库**，靠 `RecordManager` 定时做分层聚合：
  原始 1 分钟（留 1 小时）→ 10 分钟（留 12 小时）→ 20 分钟（留 24 小时）→ 2 小时（留 7 天）→ 8 小时（留 30 天）。
- Agent 侧 `DeltaTracker` 把累计计数器转成速率，与本项目「速率只用于曲线、流量只用 counter 差值」完全一致。
- 传输首选 **WebSocket**，SSH 反向隧道兜底；用 CBOR 压缩载荷。
- 内建多用户、OAuth/OIDC、可**关闭密码登录**、自动备份。

**结论**：本项目「SQLite + 写时预聚合 + 单容器 + 零外部依赖」的路线，与 Beszel 的轻量化哲学是同一类，
在个人自用场景下是合理取舍，不必强行上 Prometheus。但 Beszel 的**自动 rollup、认证可插拔、备份内建**
是本项目值得补的三块。

### 2.6 PT Nexus

[sqing33/PTNexus](https://www.togithub.com/sqing33/PTNexus) 是 PT 圈的多下载器聚合平台（Go + Python，
支持 MySQL/SQLite 多数据库），本项目 README 多处以它为参照。其 CHANGELOG 里可以看到与本项目几乎
同构的演进路径：

> v1.2「新增：下载器实时速率开关，关闭则 1 分钟更新一次上传下载量（开启为每秒一次）」、
> 「新增：下载器图表上传下载显示切换开关」、v1.2.1「修复：种子页面总上传量始终为 0 的问题」、
> 「修复：速率图表图例数值显示不完全的问题」。

这说明两点：
1. 本项目 v33 把「实时速率」与「流量统计」拆成两条独立采样线程、各自档位，
   与 PT Nexus 的「实时速率开关」是**同一个问题的两种解法**，方向正确；
2. 「总上传量为 0」「图例数值显示不全」这类问题，正是本项目 `db.py` 里用
   `COALESCE` 保住累计基线、`renderLegend()` 自适应换行所规避的坑——本项目在这些点上处理得更细。

## 四、本项目的优点（确认无需改动的部分）

1. **流量口径正确且经过验证**：只认累计计数器差值，五态异常判定（`no_base / reset / spike / missing`）
   与 Prometheus counter 语义等价，避开了「速率积分」这个行业里最常见的错误。v15 的
   `COALESCE` 基线保护修掉了「计数缺席 → 基线被 NULL 冲掉 → 持续高估」的连锁 bug。
2. **采样与统计解耦（v33）**：两条独立线程、独立客户端缓存、独立基线、独立落库。
   这一点比很多同类项目更干净——很多项目用一条采集循环同时喂实时曲线和总量，改间隔就互相牵连。
3. **绘图点密度判定（v33）**：`chart.py` 强制 `step ≥ 采样间隔`，绘制点数不超过采样点数，
   避免重复值空耗绘图。这是同类前端图表很少显式处理的问题。
4. **零第三方前端依赖 + SVG 矢量**：无 CDN、可完全离线、放大不糊、PWA 可安装，供应链攻击面极小。
5. **依赖极简**：`requirements.txt` 只有 `flask` + `waitress`，镜像 132 MB，无 Redis / 无 TSDB / 无 Node。

## 五、逻辑结构 / 代码实现 / 算法上可优化的点

按「影响面 × 改造成本」排序，均给出具体位置。

### 5.1 【高】长短窗口数据源拼接，是最大的结构性技术债

`chart.py` 里速率图长窗口走 `hourly`（自适应小时整数倍分桶），短窗口走 `samples`，
流量统计短窗口还要 `UNION ALL traffic_samples + 旧 samples`（v33 兼容历史数据），
再加上 `samples_min_ts / hourly_min_ts / traffic_min_ts` 三个起点判断回退逻辑。

问题：
- `build()` 里为算 `max_offset` 会**先完整调用一次 `_buckets()`**，再正式调用一次，重复计算；
- 三张表的 `MIN(ts)` 每次请求都查；
- 兼容旧数据的 `UNION ALL` 会随历史数据量线性变慢，且 `samples` 与 `traffic_samples`
  语义不同（前者 `dl_inc` 恒 0），混在一张图里靠注释约定，维护风险高。

建议：引入 **Beszel/Netdata 式的自动 rollup**——采集时只写一张 `raw` 明细表，
后台定时任务把它聚合到 `1m / 1h / 1d` 三张物化表，查询时按窗口跨度**只选一张表**。
这样能删掉 `UNION ALL`、三处 `MIN(ts)`、近细远粗的混合分支，`chart.py` 可瘦一半以上，
且天然支持任意长的时间范围。这是**最值得做的重构**。

### 5.2 【中】双线程仍有隐含耦合

`collector.py` 的速率线程与流量线程各自 `fetch()`，但共享同一台下载器的
`downloader_state` 行（速率线程写 `rate_last_*`，流量线程写 `last_*`），以及同一个
`db.conn()` / WAL。高频档位（0.1 秒）下：
- 速率线程每 0.1 秒一次 `UPDATE downloader_state`，与流量线程的写事务争 SQLite 写锁；
- `db.set_offline()` 在失败时更新状态，两个线程都可能写，存在相互覆盖在线状态的竞态。

建议：速率线程的瞬时状态（速率、在线、错误）放**内存 / 独立轻量表**，不持久化到
`downloader_state`；`downloader_state` 只由流量线程维护累计基线。可彻底消除写竞争，
也顺带省掉 0.1 秒档位下的磁盘写放大。

### 5.3 【中】轮询 → 推流，可显著降低高频档位的开销

前端目前是固定间隔轮询 `/api/overview` + `/api/chart`（`app.js` 里 1 秒刷新实时档）。
0.1 秒采样档位下，服务端已被采集线程压着，前端还要各自发 HTTP 请求。
VueTorrent / ntopng / Beszel 都用 **SSE 或 WebSocket 推增量**。
建议：加一个 `/api/stream`（SSE），后端在采集完成时推一次增量，前端只做局部更新；
低频档位仍可保留轮询降级。改造量中等，收益在高频档位明显。

### 5.4 【中】`niceMax` 的「贴合」与 Y 轴刻度语义冲突（本轮已部分处理）

v34 把峰值贴合系数从 0.82 提到 0.98 后，Y 轴最大刻度值就等于 `peak/0.98`，
不再是 1/2/5 系列的「整刻度」。这在视觉上更饱满，但刻度数字会变成
`1.071 M`、`1.224 M` 这类非整数，读起来不如 `1.2 M` 自然。
`niceMax()` 里已有 `if (peak/max < Y_FILL - 0.04) max = target;` 的兜底，
让利用率稳定在 94%~98%。若后续要求「刻度必须是整数」，建议把「绘图上限」与
「刻度上限」拆成两个值：绘图用 `peak/0.98`，刻度仍取 nice 数并单独标注，二者解耦。

### 5.5 【低】工程化与可观测性

- `main.py` 里 `_detail_cache` / `_summary_cache` 是模块级全局字典 + 锁，多 worker 下不共享；
  当前 waitress 单进程 4 线程没问题，但若以后换多进程会失效。建议至少加个注释标明前提。
- 无结构化日志、无采集失败计数指标、无 `/api/metrics`。个人自用可接受，但排障时只能看
  `last_error`。建议暴露一个 Prometheus 格式的最小指标端点，便于以后接 Grafana。
- 前端 `app.js` 单文件 2000+ 行、`style.css` 多轮补丁叠加（v14/v18/v21/v25/v28/v31/v32/v34
  共 8 段补丁区），CSS 存在多处同特异性覆盖。功能没问题，但继续迭代容易踩覆盖顺序的坑。
  建议下个大版本做一次 CSS 归并。

## 六、公网暴露（lucky 反代 + 三级域名）安全风险审查

### 6.0 先纠正一个常见误解

**三级域名不是安全边界，也不具备隐蔽性。** 只要为该域名签发了 TLS 证书，
证书就会进入 **Certificate Transparency（CT）公开日志**，Shodan / Censys / ZoomEye /
各类子域名枚举工具会立刻收录；全网扫描器与批量弱口令脚本会持续访问。
「我自己个人自用、别人猜不到域名」这个假设在 2026 年不成立。必须按**面向公网的生产服务**标准加固。
另外，反代只是「加了一层」，**后端 8080 端口如果仍直接映射/可达，认证可被整层绕过**（见 6.2）。

### 6.1 风险清单（按严重程度）

| 编号 | 等级 | 风险 | 代码位置 / 证据 | 后果 |
|---|---|---|---|---|
| R1 | **严重** | **默认账号竞速接管**：`admin/admin` 是公开常量，首次登录强制改密（`must_change`），但**谁先登录谁就能调用 `/api/auth/setup` 把账号密码改成自己的**，真正的主人被锁在门外 | `auth.py:18-19,55-60,131-149`；`main.py:124-131,64-65` | 容器一启动到主人首次登录之间的窗口内，攻击者可完全接管；接管后能看到所有下载器地址与凭据 |
| R2 | **严重** | **认证后 SSRF + 下载器凭据外泄**：`/api/downloaders/test`（新建，无需已存在的 id）接受任意 `url` 并由服务端发起请求；`clients.py` 无 scheme / host 白名单，支持 `http/https/file/ftp`；`/api/downloaders/<id>/test` 在密码留空时**沿用库中已存密码**，可把下载器账号密码 POST 到攻击者服务器 | `main.py:393-420`；`collector.py:239-255`；`clients.py:230-267,506-528`（`Authorization: Basic`） | 从公网 → 登录后 → 探测容器内网、`127.0.0.1` 其他服务、云元数据 `169.254.169.254`、读取容器内文件；把 qB/Transmission 凭据带出去 |
| R3 | **高** | **错误信息回显放大 SSRF**：测试接口把原始异常字符串直接返回 | `main.py:407-409,418-420` 的 `_err(exc)` | 内网端口开放与否、HTTP 状态码、响应片段可作为回显通道，形成可用的内网探测器 |
| R4 | **高** | **登录限速在反代下失真**：`_ip()` 用 `request.remote_addr`，反代后恒为 lucky 的内网 IP。所有外部用户共享同一个失败计数器（5 次 / 60 秒） | `auth.py:63-88` | ① 一人爆破 → 全员被锁 60 秒（易被利用成 DoS）；② 限速实际上退化成「全局开关」，无法按攻击者隔离；③ 若日后为修它而盲目信任 `X-Forwarded-For`，攻击者可**伪造 XFF 绕过限速** |
| R5 | **高** | **会话 token 有效期 10 年、无绑定、无轮换**：`SESSION_TTL = 3650*86400`，token 存 localStorage，不绑定 IP / UA / 设备，无主动失效列表 | `auth.py:21,100-101` | token 一旦因 XSS、设备丢失、日志泄露而外泄，等于**十年有效期的全权通行证**；只能靠「退出登录」或「改密码」（删其他会话）撤销 |
| R6 | **中** | **未鉴权接口泄露信息**：`/api/health` 暴露内部配置（采样间隔、时区、服务器时间、采集轮次、错误）；`/api/auth/status` 暴露**登录用户名** | `main.py:49,98-106,149-163` | 攻击者省去猜用户名这一步，只剩密码爆破；同时可做应用指纹识别 |
| R7 | **中** | **缺少浏览器侧安全响应头**：全站只设了 `Cache-Control`，无 CSP / `X-Frame-Options` / `X-Content-Type-Options` / `Referrer-Policy`；HSTS 依赖 lucky | `main.py:70-74` | 一旦出现任何 XSS，localStorage 里的长期 token 直接被盗；可被引擎 iframe 嵌套做点击劫持 |
| R8 | **中** | **PBKDF2 轮数偏低**：`120_000` 轮（2021 年 OWASP 建议值） | `auth.py:20` | 2026 年 GPU 算力下，弱口令离线破解成本已明显下降 |
| R9 | **中** | **下载器密码明文存 SQLite**：`downloaders.password` 明文，`config.json` 亦可能含明文；数据卷挂到宿主机 | `db.py:125,356-365,481-530` | 数据库文件或备份泄露 = 下载器凭据泄露（ albeit 前端 GET 已用 `public=True` 把 password 换成 `has_password`，未直接回显，这点做得对） |
| R10 | **中** | **无全局限流 / 请求体上限**：`before_request` 只做鉴权，无速率限制；waitress 仅 4 线程 | `main.py:56-67`；`Dockerfile CMD --threads=4` | 登录后高频打 `/api/chart`（每次全表聚合 + 补零）或超大 body，可耗尽 4 个线程造成拒绝服务 |
| R11 | **中** | **反代被绕过**：若容器 `8080` 端口直接映射到宿主机公网 / 与 lucky 同网段可直连，攻击者可用 `IP:8080` 绕开 lucky 的 BasicAuth / IP 白名单 | `docker-compose.yml` 的 `ports: "${WEB_PORT:-8080}:8080"` | 边界防护整层失效，只剩应用自己的登录 |
| R12 | **低** | **无审计日志**：登录成功 / 失败、配置变更、下载器增删改均无持久化记录 | 全项目 | 出事无法回溯「谁在什么时候改了什么」 |
| R13 | **低** | **CSRF**：token 存 localStorage 并靠 `Authorization` / `X-Auth-Token` 自定义头传递，浏览器跨站表单不会自动携带 | `auth.py:105-109`；`app.js` api() | 实际不可利用，风险低；但若引入 Cookie 认证则必须补 CSRF Token |

> 补充核查（**未发现问题**的部分，一并说明避免误判）：
> - SQL 注入：`stats.query_stats()` 用 `GRANULARITIES` 白名单校验粒度、列名来自常量映射
>   `GRAN_COLUMN`，`chart.build()` 校验 `range` / `metric` 白名单，`db.py` 全部参数化 → **封闭**。
> - XSS：前端 `esc()` 覆盖了名称 / URL / 错误信息 / 颜色等所有插入 `innerHTML` 的动态值 → **基本封闭**。
> - 资源耗尽：`timeutil.generate_keys()` 有 `limit=2000`、`chart.build()` 的 `offset` 上限 30 个窗口
>   → **已有防护**，R10 主要指并发放大而非单点爆炸。
> - Service Worker：`sw.js` 明确不缓存任何 `/api/` 响应、只缓存静态外壳 → **不会缓存含凭据的数据**。
> - WSGI：用 waitress（非 Flask 开发服务器），`USER 1000:1000` 非 root 运行 → **部署基线良好**。

### 6.2 「被穿透」的三条现实路径

1. **绕开反代直接打后端**：`IP:8080` 或同网段直连 → lucky 的 BasicAuth / IP 白名单全部失效。
   *对策见 7.1*。
2. **抢在主人之前完成初始化**：R1，纯应用层，与反代无关。
   *对策见 7.2*。
3. **登录后借应用自身能力打内网**：R2/R3，即「把公网入口当成内网探测跳板」，
   这是最容易被忽略的一类——反代只挡外面的人，挡不住「已登录用户让服务端主动往外连」。
   *对策见 7.3*。

### 6.3 加固方案

#### 7.1 【必须】边界层（lucky）

按 [lucky 反代实战](https://blog.csdn.net/gitblog_02091/article/details/145053006) 与
[安全加固解析](https://tsight.io/articles/18531397) 的社区最佳实践：

- **给该三级域名的子规则开启二次认证**（BasicAuth 或 Lucky 的「网页认证」），
  形成「反代认证 + 应用登录」双层。即使应用出现 R1/R5 也多一道锁。
- **HTTPS 强制**：443 主规则终结 TLS，HTTP 自动跳 HTTPS；后端全走 HTTP 即可。
- **IP 白 / 黑名单 + UA 过滤**：个人自用建议白名单模式；若用 IPv6 直连，务必在**路由层**
  只放行 80/443，避免 IPv6 下内网设备被直接扫到。
- **默认子规则设为「关闭连接」**，别让泛域名暴露服务指纹。
- **信任代理 IP 要收紧**：只有确认了「可信代理网段」才启用 `X-Forwarded-For` 识别；
  配得太宽会让人伪造头绕过 IP 过滤。
- **关键：让容器只监听内网 / 回环**。把 compose 的端口映射改成
  `127.0.0.1:8080:8080`（仅 lucky 本机可达），或用独立的 docker 网络让 lucky 与容器互通、
  不对宿主机暴露 8080。这样 R11 直接消失。

#### 7.2 【必须】首次部署流程

- **不要用默认账号启动后立即暴露公网**。建议：先在**内网**用 `admin/admin` 登录并完成
  `/api/auth/setup` 改成强账号强密码，再开启 lucky 的公网规则。
- 更彻底的做法（推荐给下一轮代码迭代）：给 `config.py` 增加 `BOOTSTRAP_USERNAME` /
  `BOOTSTRAP_PASSWORD` 环境变量，`auth.bootstrap()` 优先用它们建号并把 `must_change` 置 0，
  从根上消除 R1 的竞速窗口。

#### 7.3 【必须】修 SSRF 与凭据外泄

在 `clients.py::make_client()` / `collector.test()` 入口加统一 URL 校验（可直接采用）：

```python
# 建议加入 app/netsafe.py
import ipaddress, socket, urllib.parse

def assert_safe_target(url: str, allow_private: bool = False):
    p = urllib.parse.urlsplit(str(url))
    if p.scheme not in ("http", "https"):
        raise ValueError("只允许 http / https")
    host = p.hostname or ""
    if not host:
        raise ValueError("URL 缺少主机")
    # 解析所有 A/AAAA 记录，防 DNS rebinding
    infos = socket.getaddrinfo(host, p.port or (443 if p.scheme == "https" else 80))
    for info in infos:
        ip = ipaddress.ip_address(info[4][0])
        if not allow_private and (ip.is_private or ip.is_loopback or
                                  ip.is_link_local or ip.is_reserved or ip.is_multicast):
            raise ValueError("禁止访问内网 / 环回 / 保留地址")
    return p.geturl()
```

配合三条改动：
1. `test` 类接口调用前先 `assert_safe_target(url)`；
2. **禁止「测试新 URL 时沿用已存密码」**——`main.py:404-405` 那段改成：url 与库中不一致时
   必须显式提供密码，否则直接拒绝（堵死凭据外泄）；
3. `_err(exc)` 改成统一文案（如「连接测试失败」），把原始异常只写服务端日志，不回显（堵死 R3）。

> 注意：如果下载器本身就在内网（绝大多数场景），需要允许**配置中已保存的那些**内网地址，
> 但要对「测试接口临时传入的新地址」严格校验。建议维护一份「已授权下载器地址白名单」，
> 而不是全局放开 `allow_private`。

#### 7.4 【强烈建议】会话与限速适配反代

- `auth._ip()` 改为：仅当 `request.remote_addr` 属于**可信代理网段**（环境变量配置）时，
  才读 `X-Forwarded-For` 的**最后一跳**；否则一律用 `remote_addr`。杜绝伪造 XFF 绕过。
- `SESSION_TTL` 从 3650 天降到 **7~30 天**，并加滑动续期；token 绑定 IP 段 / UA 指纹，
  变化时要求重新登录。
- `PBKDF2_ROUNDS` 提到 **600_000**（OWASP 2023 建议值），并对旧哈希做登录时透明升级。
- `/api/auth/status` 去掉 `username` 字段（前端只需 `authenticated` / `must_change`）；
  `/api/health` 收敛为只返回 `{"ok": true}`，内部指标移到需鉴权的 `/api/overview`。

#### 7.5 【建议】响应头与限流

在 `main.py::after_request` 统一加：

```python
resp.headers.setdefault("X-Content-Type-Options", "nosniff")
resp.headers.setdefault("X-Frame-Options", "DENY")
resp.headers.setdefault("Referrer-Policy", "no-referrer")
resp.headers.setdefault("Content-Security-Policy",
    "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; "
    "img-src 'self' data:; connect-src 'self'; object-src 'none'; frame-ancestors 'none'")
app.config["MAX_CONTENT_LENGTH"] = 256 * 1024   # 请求体上限
```

再加一个轻量的按 token / IP 的全局令牌桶（如 60 次/分钟），重点保护 `/api/chart` 与
`/api/downloaders/*/test`。HSTS 由 lucky 统一设置即可。

#### 7.6 【建议】凭据与审计

- 下载器密码改用 `Fernet` / `cryptography` 加密后存库，密钥由环境变量注入；
  或至少把 `config.json` 权限设为 `600` 并加进 `.gitignore`（当前已在 `.gitignore`）。
- 增加 `audit_log` 表，记录登录成功 / 失败、账号变更、下载器增删改、连接测试的目标 URL。

## 七、结论

1. **架构与算法层面**：本项目「累计计数器差值 + 写时预聚合到 SQLite + 双线程采样分离 +
   绘图点密度判定」的路线是**正确且经得起同类项目验证**的，与 Prometheus counter 语义、
   Beszel 的 DeltaTracker、PT Nexus 的实时/统计分离思路一致。单容器零依赖是个人自用场景的合理取舍。
   **最值得做的结构性优化是 5.1 的自动 rollup 重构**，其次是 5.2 消除双线程写竞争、5.3 引入 SSE 推流。
2. **公网暴露层面**：代码本身没有「一键 RCE」式漏洞，SQL 注入 / XSS / 路径穿越等常规面封闭得不错，
   部署基线（waitress + 非 root + 极小依赖）也良好。但**它默认是按「内网可信环境」设计的**：
   R1 默认账号竞速、R2 认证后 SSRF、R4 反代下限速失真、R5 十年 token 这四项，
   在「lucky 反代 + 公网三级域名」场景下会被显著放大。
   **只要按 7.1~7.3 做边界收敛、部署顺序调整、SSRF 校验，风险即可降到可接受水平**；
   7.4~7.6 属于纵深加固，建议排入后续版本。
3. **本轮 v34 的处理范围**：按你的要求只落地了三项界面改动（设置页横向导航、绘图区 98%、
   删除说明并重做图例），**未改动任何认证 / 网络相关代码**——因为 R1~R5 的修复会改变现有登录与
   部署习惯（例如内网地址白名单、初始账号环境变量），需要你先确认再实施。上文的补丁片段可直接采用，
   也可作为下一轮迭代的需求输入。
