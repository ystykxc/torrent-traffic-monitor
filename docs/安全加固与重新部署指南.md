## 1. 代码修不了 / 必须部署侧配合的问题（详细应对方案）

### 1.1 【必须】边界层：lucky 反代二次认证（R1/R5 的纵深防御，R11 的剩余面）

代码已经消除了 R1 的竞速窗口、给 R5 加了绑定与短有效期，但**应用登录永远只是第二道锁**。一旦应用自身出现未知漏洞、或 token 被 XSS/设备丢失泄露，反代认证是唯一挡在前面的东西。请按下面配置：

1. **给这个三级域名的子规则开启二次认证**（lucky：子规则 → 「前端鉴权 / 网页认证」，或直接用 BasicAuth）。效果是所有请求先过一层账号密码，再到应用登录页，形成双层。
   - 不要复用 `BOOTSTRAP_*` 的账号密码，反代认证单独生成一组。
   - BasicAuth 密码建议 `openssl rand -base64 24` 生成。
2. **HTTPS 强制**：443 主规则终结 TLS，HTTP 自动 301 跳 HTTPS；容器内部走 HTTP 即可。
3. **HSTS**：在 lucky 主规则加 `Strict-Transport-Security: max-age=31536000; includeSubDomains`。应用不设 HSTS（HSTS 必须在 TLS 终结层下发，容器里设了也不会被浏览器正确接受）。
4. **IP 白 / 黑名单 + UA 过滤**：个人自用建议白名单模式；若必须公网可访问，至少开启 lucky 的「限制访问频率」作为上游限流（应用层 R10 限流是最后一道，不是容量层）。
5. **默认子规则设为「关闭连接」**（拒绝泛域名），避免 `*.your.domain` 直接暴露服务指纹。
6. **不要再把 8080 映射到 `0.0.0.0`**。v35 两个 compose 已改成 `127.0.0.1:8080:8080`，只有本机 lucky 能连。
   - 如果 lucky 与容器**不在同一台宿主机**：二选一 ——
     - ① 把 lucky 和容器放进同一个 docker 网络，保持 `127.0.0.1` 绑定不变（推荐）；
     - ② 改成 `- <宿主机内网IP>:${WEB_PORT:-8080}:8080`，并在宿主机防火墙只放行该来源 IP。

> 验证方法：在另一台设备上直接访问 `http://<宿主机IP>:8080`，应**连接被拒绝/超时**；只有经三级域名 + HTTPS 才能打开。

### 1.2 【必须】IPv6 与宿主机防火墙（R11 常被漏掉的一半）

compose 的 `127.0.0.1:...` 只约束 IPv4。**如果域名有 AAAA 记录、或宿主机有公网 IPv6 地址，IPv6 直连仍可能绕开 lucky**。这是纯网络层问题，应用代码完全无法感知：

- **路由器 / 上级防火墙只放行 TCP 80、443 入站**，明确不放行 8080（以及其它高位端口）的 IPv6 入站。
- 若不需要 IPv6 公网访问，**不要为该三级域名发布 AAAA 记录**；或在 DNS 只发 A 记录。
- 飞牛 / Linux 宿主机可用 `ip6tables` 兜底（示例，按实际网卡名调整）：
  ```bash
  ip6tables -A INPUT -p tcp --dport 8080 -j DROP
  ip6tables -A INPUT -p tcp -m multiport --dports 80,443 -j ACCEPT
  ```
- 检查：`curl -6 -sS http://[宿主机IPv6]:8080/api/health` 应不通；`ss -ltnp` 里 8080 应只出现在 `127.0.0.1` 而不会出现在 `:::8080`。

### 1.3 【必须】可信代理网段 `TRUSTED_PROXIES`（R4）

v35 的 `client_ip()` 只在 `remote_addr` 属于 `TRUSTED_PROXIES` 时才读 `X-Forwarded-For` 最后一跳。**留空 = 不信任任何 XFF**，此时反代后所有外部用户共用同一个反代 IP 计数：限流会互相影响、审计日志里 IP 全是反代地址、会话 IP 绑定失效。因此公网反代部署**必须**配置它，但也**绝不能配宽**。

如何确定该填什么：

1. 先起容器，在容器里看连接来源（或临时看 `/api/audit` 的 `ip` 字段）：lucky 与容器同机走 docker 网桥时通常是 `172.17.0.1`；用 `host` 网络或同机反代时是 `127.0.0.1`；lucky 在另一台设备时是那台设备的内网 IP。
2. 写成尽量窄的 CIDR，多个用逗号分隔：
   ```dotenv
   TRUSTED_PROXIES=172.17.0.1/32
   # 或多个：TRUSTED_PROXIES=127.0.0.1/32,172.17.0.1/32
   ```
3. **不要**写 `0.0.0.0/0`、`10.0.0.0/8` 这类宽网段：那等于任何能直连容器的人都能用伪造 XFF 绕过限流与 IP 绑定。
4. v35 的 `Dockerfile` 已加 `--no-clear-untrusted-proxy-headers`，让 waitress 保留原始 XFF 交给应用判断；waitress 未配置 `trusted_proxy`，因此不会改写 `REMOTE_ADDR`，可信链判断始终基于真实 socket 对端地址。**若你自行覆盖 `command:`，务必保留这个参数**，否则 R4 修复会静默失效。
5. 验证：
   ```bash
   # 从可信代理网段带 XFF 请求，审计日志应记录 XFF 里的 IP
   curl -s -H 'X-Forwarded-For: 203.0.113.9' -H "Authorization: Bearer $TOKEN" \
     https://你的域名/api/audit
   # 直连宿主机 8080 并伪造 XFF，ip 仍应是真实对端 IP（伪造不生效）
   ```

### 1.4 【必须】密钥管理与备份（R9）

应用已把下载器密码加密存库，但**密钥由谁保管、怎么备份，是纯运维决策**。做错一步会导致「数据卷恢复后所有下载器密码解不开、采集全部失联」。

- **显式设置 `SECRET_KEY`**（不要依赖自动生成的 `.secret_key`）：
  ```bash
  openssl rand -hex 32
  ```
  写进同目录 `.env`，并 `chmod 600 .env`。
- **密钥与数据卷分开备份**：`data/traffic.db` 和 `data/.secret_key` 放在一起泄露 = 加密可被解开。理想做法是 `SECRET_KEY` 只存在 `.env`（单独加密备份），数据卷备份不包含 `.env`。
- **关于 `data/.secret_key`**：v35 会自动维护这个文件作为**持久回退密钥**（即使你用 `SECRET_KEY`，也会补写一份）。**不要手动删除它**——删除后再移除 `SECRET_KEY` 会导致历史密文无法解密。
- **v35 的兼容性设计**：`decrypt()` 会依次尝试 `SECRET_KEY` 派生密钥与 `.secret_key` 文件密钥；`init_db()` 启动时会把能用回退密钥解开的历史密文 rekey 到当前主密钥（日志会打印「已用当前主密钥重加密 N 个历史下载器密码」）。所以「先默认启动、后补 `SECRET_KEY`」或「更换 `SECRET_KEY`」都不会把已保存密码弄丢。
- **仍然要避免**：定期随意轮换 `SECRET_KEY` 又不保留旧 `.secret_key`。轮换本身安全（多密钥回退会处理），但请保留数据卷里的 `.secret_key` 直到确认所有历史密文都已 rekey。
- `config.json` 可能含明文下载器密码（首次导入用），保持 `chmod 600`，且它已在 `.gitignore` 中。

### 1.5 会话、浏览器侧与 R13（CSRF）

- **升级后请主动清理浏览器**：v35 启动时会作废旧的长效会话（`max_expires_at<=0` 一律删除），但浏览器 `localStorage` 里可能还存着旧 token。请在部署后**退出登录并重新登录一次**，或清掉该站点的本地存储。
- **不要禁用 `SESSION_BIND`**（默认 `1`）。UA / IP 网段变化会要求重新登录：这是 R5 的核心。若你在移动网络频繁切换导致困扰，可设 `SESSION_BIND=0`，但要知道这等于放弃 IP/UA 绑定。
- **HSTS 仍由 lucky 负责**（见 §1.1），应用 CSP 已覆盖 XSS/点击劫持主要面。
- **R13 CSRF 当前不可利用**：token 存 `localStorage`、靠 `Authorization: Bearer` / `X-Auth-Token` 自定义头传递，浏览器跨站表单不会自动携带，且 CSP 的 `form-action 'self'`、`frame-ancestors 'none'` 进一步收紧。**约束条件**：如果将来改成 Cookie 认证、或引入任何「浏览器自动携带凭据」的机制，必须同步补 CSRF Token（SameSite + 双提交 / 同步令牌），否则 R13 会立刻从「低」升级为「高」。这是设计约束，不是当前缺陷。

### 1.6 【工程化前提】单进程多线程，不要擅自多 worker（5.5）

v35 的限流计数、`_detail_cache` / `_summary_cache`、`EventBus` SSE 订阅、`db.bounds()` 缓存、`_live` 实时态**全部是进程内内存**，只在「单进程 + 多线程」下正确 —— 当前 `Dockerfile` 用 waitress 单进程 12 线程，完全匹配。

若你改成 `gunicorn -w N`、`waitress --threads` 之外的多进程、或 k8s 多副本，会出现：限流被绕过、SSE 只推到本进程的订阅者、详情缓存不一致、内存实时态各副本不同。**那时必须**：把限流计数与缓存迁到 Redis，把 EventBus 换成 Redis Pub/Sub 广播，把 SSE 做成共享订阅。这不是当前缺陷，是部署形态约束。

### 1.7 明确无法由应用代码解决的根本边界

请如实认知，以下不属于「代码能修」的范畴，只能靠运维与边界策略：

| 边界 | 说明 | 应对 |
| --- | --- | --- |
| 宿主机 / root 被攻破 | 攻击者可直接读 `data/`、改容器、抓内存 | 宿主机最小化、及时补丁、不要用 root 跑无关服务 |
| 数据卷 + 备份整体泄露 | 加密也挡不住（密钥同卷） | §1.4 密钥分离备份；备份文件加密 |
| 下载器自身弱口令 / 无认证 | 应用只是客户端，管不到 qB / TR 自身 | 给下载器设强密码、限制其监听地址、不要公网暴露 |
| 带宽耗尽型 DDoS | 应用限流只保护线程，不保护上行带宽 | CDN / 上游限速 / lucky 频率限制 |
| TLS 私钥、域名、DNS 劫持 | 在应用之外 | 证书与账号保护、DNSSEC / 注册商二次验证 |
| 反代配置错误 | 配错子规则等于没配 | §1.1 验证清单逐条核对；改配置后复测 |
| 内网横向移动 | 容器与下载器 / NAS 同网段 | VLAN / 防火墙分段，容器只放通需要的下载器端口 |

## 2. 通过 compose 重新部署（完整步骤）

> 本轮改动较大（DB schema 迁移、新表、密码加密、会话作废、SSE）。按你的授权「可以重新部署、不用考虑历史数据」，下面以**全新部署**为主。若想保留旧数据，看 §2.4。

### 2.0 准备 `.env`（两个场景通用）

在 `docker-compose*.yml` 同目录创建 `.env`，权限 600：

```dotenv
# 首次启动直接建强账号，消除 admin/admin 竞速窗口（R1）
BOOTSTRAP_USERNAME=your_admin_name
BOOTSTRAP_PASSWORD=用_openssl_rand_生成的强密码

# 下载器密码加密主密钥（R9），与数据卷分开备份
SECRET_KEY=用_openssl_rand_-hex_32_生成

# 可信反代网段（R4），按 §1.3 实测填写；不确定就先留空
TRUSTED_PROXIES=172.17.0.1/32

# 可选
WEB_PORT=8080
SESSION_BIND=1
SESSION_TTL_DAYS=30
ALLOW_PRIVATE_TARGETS=1        # 设 0 = 严格模式，测试连接只允许已保存地址访问内网
```

```bash
chmod 600 .env
```

### 2.1 场景 A：离线镜像版（推荐，你手上就有 v35 tar）

```bash
# 1) 停止并移除旧容器（保留旧镜像/卷以便回滚）
docker compose -f docker-compose.offline.yml down

# 2) 【可选】备份旧数据；按你的授权可跳过/直接清空重来
#    tar czf ttm-backup-v34.tgz ./data ./config.json ./.env
#    全新部署：rm -rf ./data && mkdir -p ./data
```

### 2.3 部署后的收尾（别漏）

1. **先在内网验证**，再开启 lucky 公网规则：
   ```bash
   curl -i http://127.0.0.1:8080/api/health          # {"ok":true}，且带全套安全响应头
   curl -i http://127.0.0.1:8080/api/auth/status     # 不含 username
   ```
2. **按 §1.1 / §1.2 配置 lucky 反代、HTTPS、HSTS、二次认证、IPv6 防火墙**。
3. **首次登录**：用 `.env` 里的 `BOOTSTRAP_USERNAME` / `BOOTSTRAP_PASSWORD`，**无需**再走 admin/admin 改密流程。
4. **清理浏览器旧 token**（§1.5），退出并重新登录一次。
5. 在 Web「下载器配置」里逐个测试连接；若下载器在内网且开了严格模式，只有已保存地址能通过校验。

### 2.4 如果选择保留旧 `data` 卷（就地升级）

v35 的 `init_db()` 会自动完成迁移，无需手工 SQL：

- 补齐 `sessions` 绑定列，并**作废旧长期会话** → 所有设备需重新登录一次；
- 把 `samples` 里的历史流量增量一次性迁入 `traffic_samples`（删除 `UNION ALL` 依赖）；
- 把库里残留的明文下载器密码改写成密文；
- 建立 `rollup_1m` / `rollup_1d` / `rollup_state` / `audit_log` 表与索引；
- 用回退密钥解开历史密文并 rekey 到当前主密钥。

注意事项：

- **保留 `data/.secret_key`**（§1.4），否则旧密文可能解不开；
- 旧浏览器 token 必须重新登录；
- 历史图表数值口径保持不变（120 组对比零回归）；
- 若升级后想彻底重来，仍按 §2.1 清空 `./data` 即可。

## 3. 部署后验证清单

```bash
BASE=http://127.0.0.1:8080

# 1) 健康检查收敛 + 安全响应头
curl -sI "$BASE/api/health" | grep -Ei 'HTTP/|content-security|x-frame|x-content|referrer|permissions|cache-control'

# 2) 未鉴权接口不泄露信息
curl -s "$BASE/api/health"; echo          # {"ok":true}
curl -s "$BASE/api/auth/status"; echo     # 无 username 字段

# 3) 登录（换成你的 bootstrap 账号）
TOKEN=$(curl -s -X POST "$BASE/api/auth/login" \
  -H 'Content-Type: application/json' \
  -d '{"username":"your_admin_name","password":"你的强密码"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["token"])')

# 4) 可观测性端点
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/api/metrics?format=json"; echo
curl -s -H "Authorization: Bearer $TOKEN" "$BASE/api/audit?limit=10"; echo

# 5) SSE 推流（应看到 hello 帧，约一个采集周期后看到 rate / traffic 事件）
curl -N --max-time 12 -H "Authorization: Bearer $TOKEN" "$BASE/api/stream"

# 6) SSRF 被拦截且不回显细节
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"url":"file:///etc/passwd","type":"qb"}' "$BASE/api/downloaders/test"; echo

# 7) 端口未对外（在另一台设备执行，应不通）
#    curl -sS --max-time 3 http://<宿主机IP>:8080/api/health
```

日志里**不应**出现 `Traceback`、`AssertionError`、`crypto.tag_mismatch` 刷屏；正常只有离线/不可达下载器的 `collector.poll_failed`（若下载器本来就在线则连这个也没有）。

## 4. 新增环境变量速查表

| 变量 | 默认值 | 作用 | 建议 |
| --- | --- | --- | --- |
| `BOOTSTRAP_USERNAME` | 空 | 启动时直接建立的管理员账号（非 `admin`） | **必设**，2~32 位 |
| `BOOTSTRAP_PASSWORD` | 空 | 上述账号密码（≥6 位） | **必设**，强随机 |
| `SECRET_KEY` | 空（自动生成 `.secret_key`） | 下载器密码加密主密钥 | **必设**并与数据卷分开备份 |
| `TRUSTED_PROXIES` | 空 | 可信反代 CIDR 列表，逗号分隔 | 公网反代**必设**，尽量窄 |
| `SESSION_TTL_DAYS` | `30` | 会话滑动续期天数 | 7~30 |
| `SESSION_MAX_LIFETIME_DAYS` | `90` | 会话绝对生命周期上限 | 保持默认 |
| `SESSION_BIND` | `1` | UA / IP 网段绑定 | 保持 `1` |
| `PBKDF2_ROUNDS` | `600000` | 密码哈希轮数 | 保持默认 |
| `ALLOW_PRIVATE_TARGETS` | `1` | 测试连接是否允许访问私网新地址 | 公网建议 `0` |
| `RATE_LIMIT` | `180` | 每 IP / token 每分钟请求数（严格路径取一半） | 按需调整 |
| `SSE_ENABLED` | `1` | 是否启用 `/api/stream` | 保持 `1` |
| `AUDIT_ENABLED` | `1` | 审计日志 | 保持 `1` |
| `METRICS_ENABLED` | `1` | `/api/metrics` | 保持 `1` |
| `WEB_PORT` | `8080` | 宿主机回环绑定端口 | 按需 |

## 5. 残余风险与长期建议

- 应用已做纵深加固，但**反代二次认证 + HTTPS + IPv6 防火墙**仍是公网暴露的先决条件，不要因为「代码修好了」就省略 §1.1 / §1.2。
- `RATE_LIMIT` / SSE 订阅数 / 各类缓存都是**单进程内存态**，多副本部署前先按 §1.6 改造。
- 定期看 `/api/audit` 与结构化日志（`docker compose logs`），关注 `auth.login.failed`、`session.rejected`、`downloaders.test_failed`、`http.rate_limited`。
- 若未来要给应用加 Cookie 登录、OAuth、或任何「浏览器自动带凭据」的入口，记得 R13 的 CSRF 约束（§1.5）。
