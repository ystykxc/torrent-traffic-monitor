# 流量统计口径深度解析

> **归档说明**：本文配套 v15 版本撰写，其中的统计口径（流量只来自累计计数器单调差值、
> 绝不用「速率 × 时间」估算）在 **v50 沿用未变**。文件名已去除版本号，归档于 `docs/`。


**——为什么「下载器流量统计」与 PT Nexus 对不上账、误差从哪来、以及正确的统计逻辑**

> 配套版本：`torrent-traffic-monitor` **v15**
> 对比对象：`sqing33/PTNexus`（GitHub `go` 分支，Go 后端 + Vue3 前端）
> 本文所有 pt-nexus 结论均来自其公开源码，文件路径与行号可逐条复核。

---

## 0. 先给结论

你观察到的数字：

| 口径 | 今日上传 | 今日下载 |
|---|---|---|
| 本项目（v14 及以前） | 23 GB | 203 GB |
| PT Nexus | 20.62 GB | 190.31 GB |
| 本项目偏高 | **+11.54%** | **+6.67%** |

三句话概括：

1. **两个项目读的是同一个数据源**。qBittorrent 都读 `sync/maindata → server_state.alltime_dl / alltime_ul`，Transmission 都读 `session-stats → cumulative-stats.downloadedBytes / uploadedBytes`，单位都是字节、前端都用 1024 进制。所以差异**不是**"数据源不同"，**也不是** GB/GiB 换算。
2. **差异出在「增量怎么算」和「异常怎么办」**。PT Nexus 全程只用累计计数器的差值（`MAX(累计) − MIN(累计)`），拿不到或异常就直接跳过、不猜；本项目旧版在累计计数器暂时取不到时，会退化成 **「瞬时速率 × 采样间隔」** 并把结果**累加进流量**。后者是估算值，不是真实字节数，会系统性偏高。这是本项目偏大的**确定性根因**。
3. **v15 已把这条估算路径彻底移除**：流量只能来自累计计数器差值，任何异常轮次一律记 0、保留基线；速率只用于画实时速率曲线，绝不参与流量累加。修复后数值会向 PT Nexus 靠拢（变小），这是**变准了**，不是变小了。

还有一层需要说明：**不能把 PT Nexus 的数字当成"标准答案"**。它自身也有会让它偏小的设计（按桶 `MAX−MIN` 会丢桶边界增量、时间窗口依赖容器时区）。正确的基准只有一个：**下载器自己记账的累计计数器在两个时刻的差值**。第 5、7 节会给出可操作的核对方法。

## 1. 先把「流量」这个词拆清楚

同一个下载器上，至少有**三个互不相同**的"流量"数字，很多争议都源于把它们混为一谈：

| 类别 | 从哪来 | 本质 | 能不能当「今日流量」 |
|---|---|---|---|
| **① 累计计数器** | qB `alltime_dl/ul`、TR `cumulative-stats` | 下载器自己记账、持久保存、单调递增的**已传输字节总数**（自安装 / 上次统计清零起） | ✅ **唯一可信基准**：`C(t₂) − C(t₁)` 就是这段时间的精确流量 |
| **② 瞬时速率** | qB `dl_info_speed`、TR `downloadSpeed` | 当前这一刻的**速度**（B/s），是短窗口滑动平均 / 派生量 | ❌ 只能画速率曲线；`速率 × 时间` 是对积分的近似，有采样误差 |
| **③ PT 站 tracker 量** | tracker 的 `announce` 上报 | 客户端按种子向站点自报的 `uploaded/downloaded` 增量 | ❌ 站点口径，含 Free/不计下载规则，与本机真实网卡流量本就不相等 |

> 关键认知：**流量是"存量差"，不是"流量积分"**。累计计数器是下载器在每次传输成功后由自己累加的账本，精确到字节；而速率是给仪表盘看的观测量，用瞬时值去反推一段时间的总量，等价于用一张照片推测一段视频。

本项目与 PT Nexus 都属于"读 ①、算 ① 的差值"这一类，所以**理论上两者应该几乎相等**。对不上，只能是实现差异。

## 2. 两个项目的统计链路逐层对照

### 2.1 数据源（完全一致 ✅）

**PT Nexus** — `server/internal/service/downloaderclient/client.go`：

```go
// L102-124  qBittorrent
mainDataBody, err := client.Get("sync/maindata", nil)   // 注意：不带 rid 参数
serverState := toMap(mainData["server_state"])
return TrafficStats{
    DownloadSpeed: toInt64Any(serverState["dl_info_speed"]),
    TotalDownload: toInt64Any(serverState["alltime_dl"]),   // ← 全局累计下载
    TotalUpload:   toInt64Any(serverState["alltime_ul"]),   // ← 全局累计上传
}
// L127-150  Transmission
response, _ := client.Call("session-stats", ...)
cumulativeStats := toMap(arguments["cumulative-stats"])
TotalDownload: toInt64Any(cumulativeStats["downloadedBytes"]),
TotalUpload:   toInt64Any(cumulativeStats["uploadedBytes"]),
```

**本项目** — `app/clients.py`：

```python
# qBittorrent
"dl_total": st.get("alltime_dl"),   "up_total": st.get("alltime_ul"),
# Transmission
cum = a.get("cumulative-stats")
"dl_total": cum.get("downloadedBytes"), "up_total": cum.get("uploadedBytes"),
```

**结论：字段一模一样，单位都是字节。** 差异不可能来自"读错了接口"。

> 附带一个值得注意的细节：PT Nexus 的 `Get("sync/maindata", nil)` **不带 `rid`**，qB 默认按 `rid=0` 处理 → 每轮都返回 `full_update=true` 的完整 `server_state`。本项目旧版为了"轻量化"用了 **递增 `rid` 的增量同步**。这正是后面问题的伏笔（见 §4.1）。

### 2.2 采集频率与存储内容

| | PT Nexus | 本项目（v14） |
|---|---|---|
| 采样间隔 | 开启实时速率时 **1 秒**，否则 60 秒（`tracker.go:174-181`） | 默认 **10 秒**（`config.example.json` 可调） |
| 每次存什么 | **累计快照** `cumulative_uploaded/downloaded`；增量字段 `uploaded/downloaded` **恒写 0**（`tracker.go:234-243`） | **算好的增量** `dl_inc/up_inc` 写入 `samples`，并按时间比例分摊进 `hourly` 小时桶（`db.py:436-475`） |
| 速率存哪 | `upload_speed/download_speed` 单列，只用于速率图 | `dl_rate/up_rate` 存 `samples`，只用于速率图 |
| 原始数据寿命 | 48 小时（每 6 小时聚合进 `traffic_stats_hourly` 后删除原始记录，`tracker.go:160-169`） | `samples` 保留 7 天；`hourly` 永久 |

### 2.3 增量算法（**核心分歧**）

**PT Nexus：按时间桶取累计值极差**

`server/internal/repository/stats_repository.go:526-552`：

```sql
SELECT STRFTIME('%Y-%m-%d %H:00', stat_datetime) AS time_group,
       downloader_id,
       GREATEST(0, MAX(cumulative_uploaded) - MIN(cumulative_uploaded)) AS total_ul,
       GREATEST(0, MAX(cumulative_downloaded) - MIN(cumulative_downloaded)) AS total_dl
FROM traffic_stats
WHERE stat_datetime >= ? AND stat_datetime < ?
GROUP BY time_group, downloader_id
```

`server/internal/service/stats/chart.go` 再把各桶 `total_ul/total_dl` 累加成今日总量。
「今日」按 `%Y-%m-%d %H:00` 分桶（24 个桶），范围 = 今天 00:00 ~ now（`speed.go:188-`）。

**本项目：逐次相邻差值连续累加**

`app/collector.py`（旧）：

```python
def _increment(total, previous, rate, dt):
    if total is not None and previous is not None and total >= previous:
        value = int(total - previous)
        if 0 <= value <= MAX_ONE_TICK:
            return value
    return int(max(0, rate) * dt)          # ← 问题就在这里
```

`dl_inc = total_now - total_prev`，每轮算一次，累加到小时桶。

**数学上**，若累计计数器每轮都拿得到：

```
Σ(total_i − total_{i−1})  =  total_last − total_first      （望远镜求和，精确）
```

本项目的"连续差值累加"其实**比 PT Nexus 的"分桶 MAX−MIN"更完整**：后者每个桶独立取极差，会**丢掉桶与桶之间边界上的那一段增量**（详见 §4.2）。所以本项目方法本身没有错，错的是那一行 `rate × dt` 兜底。

### 2.4 异常处理（**第二处核心分歧**）

| 场景 | PT Nexus | 本项目（v14） |
|---|---|---|
| 本轮没拿到累计值 | 数据不写增量（仍为 0），无影响 | `dl_total=None` → **`rate × dt` 估算并累加** |
| 累计值回退（重启 / 统计清零） | `shouldAcceptCumulative` 返回 false → **`continue` 直接跳过**（`tracker.go:264-283`） | `total < previous` → **`rate × dt` 估算并累加** |
| 首次采集 / 无基线 | 只存快照，不产生增量 | `previous=None` → **`rate × interval` 凭空造一轮流量** |
| 基线被污染 | 快照表天然单调递增 | `last_*_total` 被写成 **NULL**，形成连锁退化（见 §4.1） |

**PT Nexus 的原则是「宁可少记，绝不多猜」；本项目旧版是「拿不到就估算一个补上」。** 后者必然引入系统性偏差。

### 2.5 时间窗口与单位（排除项）

- **时区**：本项目固定 `TZ_OFFSET=8`（东八区，写死在 `app/timeutil.py`，不依赖容器时区）；PT Nexus 用 `time.Now().Location()`，即**容器本地时区**（`speed.go:189`）。若 PT Nexus 容器未设 `TZ=Asia/Shanghai`（Docker 默认 UTC），它的"今日"从 UTC 00:00 起 = 北京时间 08:00 起，窗口会与本项目不同。这是一个**独立**的潜在差异源，见 §4.3。
- **单位**：两边前端都是 **1024 进制**（本项目 `app/static/app.js` 的 `fmtBytes` 用 `v /= 1024`；PT Nexus `webui/src/views/InfoView.vue:263-269` 用 `Math.pow(1024, i)`），标签都写作 `KB/MB/GB`。**所以本例不是进制问题**（见 §4.4）。

### 2.6 对照总表

| 环节 | PT Nexus | 本项目 v14 | 是否产生差异 |
|---|---|---|---|
| 数据源字段 | `alltime_dl/ul`、`cumulative-stats` | 同 | ❌ |
| 单位进制 | 1024 | 1024 | ❌ |
| 采样间隔 | 1s / 60s | 10s | 间接（影响估算幅度） |
| 增量算法 | 分桶 `MAX−MIN` | 连续差值累加 | ✅ 轻微（PT Nexus 略偏小） |
| **异常兜底** | **跳过不猜** | **`速率×时间` 估算** | ✅✅ **主因，本项目偏大** |
| **基线维护** | 快照单调 | **可能被写 NULL** | ✅✅ **放大器** |
| 时间窗口 | 容器 TZ | 固定东八区 | ✅ 可能 |

## 3. 误差来源逐条分析（按贡献排序）

### 3.1 【主因】「瞬时速率 × 时间」记账 —— 本项目确定性缺陷

#### 触发机制：qB 的 `sync/maindata` 是增量接口

qBittorrent 的 `/api/v2/sync/maindata` 用 `rid`（Response ID）做增量同步：**`rid=0`（或 rid 不匹配）返回 `full_update=true` 的全量状态；`rid` 递增时只返回「自上次以来发生变化的键」**。这一点在 qB 官方 Wiki、各类客户端库（如 `Banned.Qbittorrent` 的 SyncService 文档）中都有明确说明。

`server_state` 同样参与增量 diff：当某一轮下载/上传暂时停顿、`alltime_dl/alltime_ul` 没有变化时，**这两个键会整个从响应里消失**（`dl_info_speed` 变成 0 仍会出现，但累计键不出现）。

本项目旧版客户端是这么写的：

```python
"dl_total": _positive(st.get("alltime_dl")) if "alltime_dl" in st else None,
```

于是形成一条隐蔽的**连锁退化链**：

```
第 N 轮   下载器空闲 → alltime_dl 字段缺席 → dl_total = None
          → _increment 走 rate × dt（此时 rate≈0，暂无害）
          → db.record_measurement 把 last_dl_total 写成 NULL   ⚠️
第 N+1 轮 恢复流量，alltime_dl 回来了，但 previous = NULL
          → _increment 仍走 rate × dt，把「瞬时速率 × 10 秒」当成真实流量累加  ⚠️⚠️
第 N+2 轮 last_dl_total 恢复为正常值 → 回到差值法
```

也就是说，**每次「空闲 → 恢复」的切换都会凭空插入一轮估算流量**。而 PT 上传恰恰是高频脉冲流（做种时连接断续），切换非常频繁。

更糟的是，若用户环境存在以下任一情况，估算会变成**长期、全量**的：

- qB 版本较老，`server_state` 里压根没有 `alltime_dl/ul`（该字段是较新版本才加入、长期未进文档 —— qBittorrent Discussion #15490 专门讨论过这件事）；
- 反向代理 / API 网关改写了 `maindata` 响应；
- 下载器重启、统计被清零后的过渡期；
- 采集器刚启动、基线尚未建立。

这些情况下旧版会**整天都在用速率积分记账**，误差自然达到百分之几到百分之十几。

#### 为什么速率积分会系统性**偏高**

`dl_info_speed` 是**短窗口瞬时速率**，用它乘整个采样间隔 `dt`，等于假设"这 10 秒里速度一直等于采样那一刻的值"。PT 流量是脉冲式的，采样时刻落在波峰的概率与波动幅度相关，瞬时值的分布均值高于区间平均；再叠加 qB 速率平滑窗口、协议开销与重传计入方式等口径差异，估算值通常**高于**真实累计差值。

而**上传（做种，脉冲式）比下载（连续流）波动更剧烈**，所以估算偏差也更大 —— 这正好解释了你看到的现象：

> 上传偏高 **+11.54%**，下载只偏高 **+6.67%**，两个方向的偏差比例不同。

如果差异来自进制换算，两个方向必然是**同一个固定比例**（7.37%），而不可能一个 11.54%、一个 6.67%。**偏差比例不同，本身就是"速率估算"而非"单位换算"的指纹。**

#### 量化复现

我写了一段可复现的蒙特卡洛重放（`simulate_bias.py`，10 秒间隔、一天 8640 轮），用可调的「累计字段可见率」重放同一份真实累计计数器序列，分别按旧版口径与 v15 口径结算：

| 场景 | 真实累计差值 | 旧版（速率兜底） | v15（只用差值） |
|---|---|---|---|
| A 字段基本可见（99%）· 下载连续流 | 190.31 GiB | 190.44 GiB（+0.07%） | 190.31 GiB（+0.00%） |
| A 字段基本可见（99%）· 上传脉冲流 | 20.62 GiB | 20.66 GiB（+0.17%） | 20.62 GiB（+0.00%） |
| B 字段高频缺席（55%/45%）· 下载 | 190.31 GiB | 199.50 GiB（**+4.83%**） | 190.31 GiB（+0.00%） |
| B 字段高频缺席（55%/45%）· 上传 | 20.62 GiB | 22.15 GiB（**+7.41%**） | 20.62 GiB（+0.00%） |
| C 字段几乎全缺席（5%）· 下载 | 190.31 GiB | **203.94 GiB（+7.16%）** | 190.31 GiB（+0.00%） |
| C 字段几乎全缺席（5%）· 上传 | 20.62 GiB | **22.58 GiB（+9.52%）** | 20.51 GiB（−0.54%） |

**场景 C 几乎精确命中了你的观测值**：203.94 ≈ 203、22.58 ≈ 23，偏差 +7.16% / +9.52% 对比实测 +6.67% / +11.54%，且同样呈现"上传偏差更大"。

> 说明：这是**机制性示意**，不是对你机器的精确复原。它证明的是"速率兜底足以产生你这个量级、且上下行比例不同的偏差"，而不是断言你的环境一定是 5% 可见率。真实环境的确切占比，请按 §7 的清单实测。

### 3.2 【次因】PT Nexus 自己也会偏小

不要把 PT Nexus 当成标准答案，它有两处会让它**少记**：

1. **按桶 `MAX − MIN` 丢桶边界**。
   今日按小时分 24 个桶，每桶独立取极差。设桶 k 的最后一个累计值是 `X`，桶 k+1 的第一个累计值是 `Y`（`Y > X`），那么 `Y − X` 这段流量**既不算在桶 k，也不算在桶 k+1**，被丢弃了。一天丢 23 段边界。PT Nexus 采样 1 秒，每段只有 1 秒流量，累计约 `23/86400 ≈ 0.03%`，影响很小但方向明确。若用户关闭实时速率（间隔变 60 秒），损失会放大到约 1.7%。
2. **累计回退直接跳过**。
   `shouldAcceptCumulative` 检测到累计下降就 `continue`，该轮快照不入库。虽然 `MAX−MIN` 能跨过缺口，但重启瞬间那一小段流量仍会丢。
3. **`GREATEST(0, ...)` 与 48 小时聚合**。
   聚合 SQL 同样用 `MAX−MIN`（`stats_repository.go:333-366`），历史数据会有同样的边界损失；`WHERE stat_datetime < cutoff` 的 cutoff 取「3 天前 0 点」与「48 小时前」中更早者，旧数据被删除后不可回溯重算。

**所以"两个数字都偏"是可能的**：本项目因估算偏高，PT Nexus 因分桶略偏小。真实值在两者之间、更靠近累计计数器差值。

### 3.3 【可能】时间窗口 / 时区不一致

- 本项目：`TZ_OFFSET = 8` 写死，今日 = **北京时间 00:00 ~ 当前小时**。不随容器时区变化，行为确定。
- PT Nexus：`todayStart = time.Date(now.Year(), now.Month(), now.Day(), 0,0,0,0, now.Location())`，`now.Location()` 是**容器本地时区**。其 Docker 部署文档提供 `TZ=Asia/Shanghai` 环境变量；**若该变量未设置，容器默认 UTC**，"今日"就变成 UTC 00:00 = 北京时间 08:00 起。

窗口不同会造成**任意比例**的差异，且因为上行/下行在一天中分布不同，两个方向的偏差比例也不同 —— 与你的现象形态一致。这一项无法从代码单方面判定，需要按 §7 检查两个容器的 `TZ`。

### 3.4 【排除】1000 / 1024 进制

两边前端都用 1024 进制，标签都写 `GB`：

```js
// 本项目 app/static/app.js
do { v /= 1024; i++; } while (v >= 1024 && i < u.length - 1);
// PT Nexus webui/src/views/InfoView.vue
const i = Math.floor(Math.log(value) / Math.log(1024));
return `${parseFloat((value / Math.pow(1024, i)).toFixed(2))} ${s[i]}`;
```

所以**不是**本例差异的原因。但这里有个真实的坑值得记住：

- `1 GiB = 1024³ = 1,073,741,824 B`，`1 GB = 1000³ = 1,000,000,000 B`，**两者相差 7.37%**。
- 两个项目**都把 1024 进制的结果标成了 `GB`**，严格说应写作 `GiB`。这是行业常见的"标错单位"，会让不同工具对比时凭空产生 7.37% 的错觉。
- v15 保留 1024 进制与 `GB` 标签**不变**（与 PT Nexus 保持一致、方便直接对比），但在本文明确标注：页面上的 `GB` 实为 `GiB`。若将来要改成十进制，需前后端 + 文档一起改，否则会引入新的对不上账。

### 3.5 【认知】累计计数器自身的口径边界

即使是"正确的"累计差值，也要知道它统计的是什么：

- qB `alltime_dl/ul` 是**全局累计**，包含**已删除种子**的历史流量、包含校验失败重传等客户端自己计入的字节；它**不等于** PT 站 tracker 上报的量（站点有 Free、不计下载、passkey 等规则）。
- TR `cumulative-stats` 是**跨会话持久累计**（重启不归零），而 `current-stats` 只是本次会话。本项目和 PT Nexus 都正确使用了 `cumulative-stats`。
- 若用户在 qB/TR 里点过「重置统计」，累计值会下降 —— 这就是所谓"计数器回退"，必须由程序正确处理（v15 的做法见 §5）。

**所以"今日流量"的正确定义是：** 在明确时区下、从今日 00:00 到当前时刻、该下载器**全局累计计数器**的增量，单位字节。它反映的是**本机客户端实际传输量**，不是 PT 站账单。

## 4. 什么才是「最优的流量统计逻辑」

综合两个项目的优缺点与计量学常识，可以归纳出 7 条原则。v15 已全部落地。

### 原则 1 — 累计计数器差值是唯一可信来源

流量是**存量差**：`F(t₁→t₂) = C(t₂) − C(t₁)`。`C` 是下载器自己记账的单调累计计数器，精确到字节，不受采样间隔、速率抖动、漏采样影响。

### 原则 2 — 速率只画曲线，绝不累加

`dl_rate/up_rate` 是瞬时派生量，唯一用途是实时速率曲线与当前状态显示。**任何把 `rate × dt` 写进流量表的代码都是 bug**。这是 v15 最重要的一处修改。

### 原则 3 — 异常记 0，绝不猜测；保留基线

| 情况 | 正确做法 |
|---|---|
| 本轮没拿到累计值 | 沿用缓存的累计值 → 差值 0；**不写 NULL 到基线** |
| 首次采集 / 无基线 | 只建立基线，本轮记 0 |
| 计数器回退（重启 / 清零） | 本轮记 0，以新值重建基线 |
| 异常跳变（> 1 TiB/轮） | 丢弃本轮，记 0 |

宁可少记一轮（下一轮差值会自动补上），也不要凭空造数。

### 原则 4 — 累计差值天然具备「漏采样自愈性」

这是累计计数器方案最优雅的性质：

```
若第 N 轮采样完全丢失，第 N+1 轮算的是 C(N+1) − C(N−1)，
自动把两轮的流量一并补回，不会漏量。
```

前提只有一个：**基线不能被清空**。v15 用客户端缓存 + 数据库 `COALESCE` 双重保证。

### 原则 5 — 用连续差值分摊，不要用分桶 `MAX−MIN`

`Σ(相邻差值)` 不丢桶边界，是完整口径；`MAX(桶内)−MIN(桶内)` 会丢边界段。本项目原本就采用连续差值 + 按时间比例分摊到小时桶（`db.record_measurement`），**这一设计优于 PT Nexus，v15 予以保留**。

### 原则 6 — 时间窗口与时区必须确定

固定 `TZ_OFFSET`、所有粒度从同一张 `hourly` 表聚合，保证「今日 / 本周 / 本月 / 本年」与图表、汇总卡**同一份数据、不会对不上账**。这是本项目一直做对的。

### 原则 7 — 单位进制显式声明

统一 1024 进制，文档中明确标注 `GB 实为 GiB`；若与第三方工具对比，先确认双方进制，否则会凭空差 7.37%。

### 一句话总结

> **只信账本（累计计数器），不信仪表盘（瞬时速率）；拿不到账本就这一轮不记，绝不估；基线永不清空，差值自会补上。**

**改动前（v14）：**

```python
def _increment(total, previous, rate, dt):
    if total is not None and previous is not None and total >= previous:
        value = int(total - previous)
        if 0 <= value <= MAX_ONE_TICK:
            return value
    return int(max(0, rate) * dt)      # ← 凭空估算并累加
```

**改动后（v15）：**

```python
def _increment(total, previous):
    if total is None:                  return 0, "missing"
    if previous is None:               return 0, "no_base"
    delta = int(total) - int(previous)
    if delta < 0:                      return 0, "reset"
    if delta > MAX_ONE_TICK:           return 0, "spike"
    return delta, "ok"                 # ← 唯一的流量来源
```

### 关于历史数据（重要）

**v15 只改变此后的采集，不会回溯修正数据库里已经写入的估算流量。**

- `hourly` 表里 v14 及以前累加进去的估算字节仍然存在，所以升级后你可能会看到「今天 00:00 到升级时刻」这一段的数字仍偏高，而升级之后恢复正常。
- 如果希望从零开始干净统计：停止容器 → 备份并删除 `data/traffic.db` → 重启。代价是**丢失全部历史统计**（账户也会回到首次改密流程，需重新设置）。
- 若只想观察修复效果，不必删库：升级后等 1~2 小时，对比"升级后这一小时"的增量与下载器 API 的累计差值即可（见 §7）。

## 6. 修复后的预期

- **新采集的流量会变小、并向 PT Nexus 靠拢**，因为去掉了凭空估算的部分。这是变准了。
- **不会与 PT Nexus 完全相同**：PT Nexus 有分桶边界损失（略偏小）、时区依赖、采样间隔不同。差异应收敛到**百分之几以内**，且不再出现"上传偏高明显大于下载"这种脉冲流指纹。
- **长期稳定性提升**：下载器重启、统计清零、网络抖动、qB 增量响应字段缺席等场景不再产生虚假流量。
- 若升级后两个项目仍有较大差异，请按下一节逐项排查，优先检查**时区**与**是否重复采集**。

## 7. 如何自己核对（可操作清单）

### 7.1 拿到"标准答案"：直接读累计计数器

在**两个明确时刻**各读一次下载器的累计值，相减就是这段时间所有工具都应该贴近的真实流量。

**qBittorrent**（把地址/账号换成你的）：

```bash
# 1) 登录拿 SID
curl -s -c /tmp/qb.cookie -X POST \
  -d 'username=admin&password=你的密码' \
  http://192.168.1.11:8080/api/v2/auth/login

# 2) 读累计值（rid=0 强制全量，保证 alltime_* 一定在）
curl -s -b /tmp/qb.cookie \
  'http://192.168.1.11:8080/api/v2/sync/maindata?rid=0' \
  | python3 -c 'import sys,json; s=json.load(sys.stdin)["server_state"];
print("alltime_dl =", s["alltime_dl"], " alltime_ul =", s["alltime_ul"])'
```

**Transmission**：

```bash
curl -s -u 'user:pass' -H 'Content-Type: application/json' \
  -d '{"method":"session-stats"}' \
  http://192.168.1.14:9091/transmission/rpc \
  | python3 -c 'import sys,json; c=json.load(sys.stdin)["arguments"]["cumulative-stats"];
print("downloadedBytes =", c["downloadedBytes"], " uploadedBytes =", c["uploadedBytes"])'
```

在 `t₁`（如整点）和 `t₂`（1 小时后）各执行一次：

```
真实下载 = alltime_dl(t₂) − alltime_dl(t₁)      [字节]
真实上传 = alltime_ul(t₂) − alltime_ul(t₁)      [字节]
换算 GiB = 字节 / 1073741824
```

然后拿这个值去对本项目、PT Nexus 在**同一时间段**的读数。**谁最接近，谁就对。**

> 注意：本项目「今日」是累计的（00:00 起），所以要比较"增量"，请在两个项目的界面上记下 t₁/t₂ 时刻的今日总量再相减，或直接用图表里对应小时桶的值。

### 7.2 逐项排查清单

| # | 检查项 | 怎么查 | 若不一致 |
|---|---|---|---|
| 1 | **是否有多个实例在采集同一个下载器** | 确认本项目容器只跑了一个；检查 `docker ps` | 重复采集会让数字翻倍或异常 |
| 2 | **两个容器时区** | `docker exec <容器> date`；PT Nexus 看 compose 里 `TZ` | 给 PT Nexus 设 `TZ=Asia/Shanghai`；本项目固定东八区 |
| 3 | **「今日」窗口起点** | 两边界面显示的起始时间 | 窗口不同则数字必然不同 |
| 4 | **单位进制** | 本文 §3.4：两边都 1024 | 若第三方用 1000，固定差 7.37% |
| 5 | **qB 版本是否提供 `alltime_*`** | 用 §7.1 的 `rid=0` 命令看有没有这两个键 | 缺失时本项目 v15 会记 0 并在字段恢复后自愈；PT Nexus 会记 0 且不自愈 |
| 6 | **是否刚重置过下载器统计** | qB 选项→统计；TR 设置 | 计数器回退会让两边都短暂归零，v15 会正确重建基线 |
| 7 | **升级前后的历史数据** | 见 §5「关于历史数据」 | 需要干净基线则删库重采 |
| 8 | **观察 `counter_event`** | 本项目 `/api/overview` 的 `extra` 里带 `counter_source`/`counter_event` | 若长期是 `cached`/`reset`，说明该下载器的累计字段不稳定，值得查代理或版本 |

### 7.3 判断标准

- 本项目（v15）与"累计计数器差值"的偏差应 **< 0.1%**（只剩整数取整误差）。
- PT Nexus 与"累计计数器差值"的偏差通常 **略为负**（分桶边界损失）。
- 若本项目仍明显高于累计差值，说明还有别的采集来源或旧数据未清，按上表逐项查。

## 8. 常见误区 FAQ

**Q：是不是把 `GB` 改成 `GiB` 就能对上？**
A：不能。两边都是 1024 进制，改标签只是让标注更准确，不改变数值。v15 特意保留 `GB` 标签与 PT Nexus 一致，方便直接对比。

**Q：采样间隔调小（比如 1 秒）能不能解决？**
A：对累计差值法**没有影响**（差值与间隔无关），但会增加请求量。真正的问题是"用速率估算"，不是"采得不够密"。v15 修掉估算后，10 秒间隔已经足够准确。

**Q：PT Nexus 的数字是不是就是准的？**
A：它比 v14 的本项目更稳健（从不估算），但会因按桶 `MAX−MIN` 丢边界而**略偏小**，且时间窗口依赖容器时区。它不是权威基准；**下载器累计计数器差值才是**。

**Q：为什么升级后今天的数字还是偏大？**
A：见 §5。`hourly` 表里升级前累加的估算量不会自动消失。要么等新数据稀释，要么备份后删 `data/traffic.db` 重采（会丢历史）。

**Q：为什么和 PT 站网页上显示的流量也不一样？**
A：站点统计的是 tracker 上报量，含 Free / 不计下载 / 站点规则，且是站点侧账本；本项目统计的是**本机客户端实际传输字节**。两者本来就不该相等，见 §1 表格第 ③ 行。

**Q：能不能用 `dl_info_data`（session 累计）代替 `alltime_dl`？**
A：不建议。`dl_info_data` 是**本次会话**累计，qB 一重启就归零，会造成频繁的"计数器回退"。`alltime_*` / TR `cumulative-stats` 是跨会话持久累计，才是正确选择。
